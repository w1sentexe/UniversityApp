# Приложение успеваемости и расписания ВГУИТ

Приложение для просмотра успеваемости (и расписания — coming soon) студентов ВГУИТ. Считывает ведомости с официального ресурса `rating.vsuet.ru` и отдаёт данные по номеру зачётной книжки. Состоит из двух частей: **API-бэкенд** (сбор, обработка, выдача данных) и **PWA-фронтенд** (клиент с установкой как приложение).


## Стек технологий

**Бэкенд (API)**
* **Язык**: Python 3.12+
* **Фреймворк**: FastAPI (с автоматической Swagger-документацией)
* **База данных**: SQLite (снимок успеваемости, файл в томе; стандартный `sqlite3` + `asyncio.to_thread`)
* **Планировщик**: APScheduler (фоновый скрапинг успеваемости раз в 30 минут)
* **HTTP/парсинг**: httpx (async) + BeautifulSoup4 (lxml)
* **Логирование**: своё структурированное (формат `сообщение | k=v`, цветной вывод)

**Фронтенд**
* **PWA** на ванильном JS (service worker + manifest, ставится как приложение), раздаётся через nginx

**Инфраструктура и инструменты**
* **Управление зависимостями**: uv
* **Качество кода**: ruff (линт + формат) + pre-commit
* **Контейнеризация**: Docker, docker-compose (FastAPI + nginx)

## Как запускается проект

У проекта два сценария запуска. **Основной способ разработки — локальная отладка через VS Code** (VPS пока нет, вся работа идёт через дебаг с брейкпоинтами). Docker-стек нужен для запуска всего окружения целиком (прод-подобно).

### 1. Локальная разработка и отладка через VS Code (основной способ)

В репозитории уже лежат `.vscode/launch.json` и `.vscode/tasks.json` — запуск в один клик, с брейкпоинтами прямо в коде. Поддерживаются **Linux, macOS и Windows** (через платформенные оверрайды в задачах).

**Предпосылки:**
1. Установить зависимости (включая dev — ruff, pre-commit):
   ```bash
   uv sync
   ```
2. Открыть проект в **VS Code** → вкладка **Run and Debug**.

Докер под отладку больше не нужен: база — файл `data/rating.sqlite3`, он создаётся при первом запуске.

Нужные переменные окружения (`DB_PATH`, `PARSING_YEAR`, `PARSING_SEMESTER`) конфигурации задают сами, поэтому `.env` для отладки не обязателен. Файл `.env` можно добавить, чтобы переопределить, например, `LOG_LEVEL`.

**Три конфигурации отладки:**

| Конфигурация | Что поднимает | Когда использовать |
|---|---|---|
| **Rating** | Бэкенд на `:8000`; снапшот сохраняется между запусками | Обычная итеративная разработка |
| **Rating (Clear DB)** | То же, но файл БД удаляется перед стартом | Чистый прогон / свежий парсинг с нуля |
| **Rating (Local Fullstack)** | Бэкенд на `:8000` + раздача `front/` на `:3000` | Проверка фронта и бэка вместе локально |

**Что происходит под капотом (задачи `tasks.json`):**
* `clear-db-debug` — удаляет `data/rating.sqlite3*` (для конфигурации *Clear DB*).
* `start-frontend` — раздача статики `front/` через `python -m http.server` на `:3000` (для *Fullstack*). Фронт сам определяет порт `3000` и бьёт в API на `:8000`.
* На остановке отладки *Fullstack*: `stop-frontend` гасит раздачу статики.

В режиме отладки можно ставить брейкпоинты в любом месте (`parsing_pipeline.py`, `parser_service.py`, роутеры и т.д.) и пошагово проходить как цикл парсинга, так и обработку API-запросов.

> На пустой базе приложение запускает первый цикл парсинга сразу после старта (с небольшой задержкой, чтобы не влезать в стартовые логи uvicorn). Если данные уже есть — ждёт очередного запуска по расписанию.

### 2. Весь стек в Docker (FastAPI + nginx)

Для запуска всего окружения в контейнерах:

1. Скопируйте файл конфигурации окружения:
   ```bash
   cp .env.example .env
   ```
   *(при необходимости отредактируйте `PARSING_YEAR`, `PARSING_SEMESTER`, `LOG_LEVEL`)*
2. Запустите docker-compose:
   ```bash
   docker-compose up --build
   ```

После этого:
* **API**: `http://localhost:8000`
* **Swagger-документация**: `http://localhost:8000/docs` (эндпоинты предзаполнены тестовой зачёткой `247162` для быстрого ручного теста)
* **Фронтенд** (nginx): `http://localhost:80`

## Уровни логирования (`LOG_LEVEL`)

Уровень задаётся переменной `LOG_LEVEL` (по умолчанию `INFO`). Принимаются стандартные значения:

* **`INFO`** (по умолчанию) — ключевые этапы: старт сервисов, подключение к БД, границы и итоги этапов парсинга, прогресс, логи запросов. Подробности по каждой ведомости скрыты.
* **`DEBUG`** — полная техническая картина: пошаговая обработка каждой ведомости, списки групп по факультетам, детали HTTP-запросов и ретраев.
* Также поддерживаются `WARNING`, `ERROR`, `CRITICAL`.
* **`DEV`** — легаси-алиас, эквивалентен `INFO` (для совместимости со старым `.env`).

Формат строки: `[время][уровень][трассировка][файл:строка] сообщение | поле=значение …`. Структурированные поля (`k=v`) добавляются логгером `get_logger()` из `app/logging_config.py`.


## Качество кода (ruff + pre-commit)

* **Линт и формат** — `ruff` (конфиг в `pyproject.toml`):
  ```bash
  ruff check app/       # линт (с автофиксом: --fix)
  ruff format app/      # форматирование
  ```
* **pre-commit** — прогоняет ruff и базовые проверки на каждый коммит. Контрибьютору достаточно один раз выполнить:
  ```bash
  pre-commit install
  ```
  Ручной прогон по всем файлам: `pre-commit run --all-files`.

## Логика работы сервиса Рейтингов

### Архитектура и структура кода
Проект построен по слоям: `router → service → repository`. Логика цикла парсинга вынесена в отдельный пайплайн, планировщик — только триггер.

```
app/
  main.py                        # сборка FastAPI, планировщик и его единственная задача run_parsing_cycle
  config.py                      # настройки, сгруппированные по подсистемам (см. ниже)
  logging_config.py              # структурированный логгер (get_logger), формат, ASCII-баннер
  sqlite_conn.py                 # движок, фабрика сессий, PRAGMA (WAL), создание таблиц
  entities/
    schemas/                     # pydantic: что уходит клиенту и ходит между слоями
      rating.py                  # всё про рейтинг: VedType, Grade, RatingVedModel, NotRatingVedModel
      schedule.py                # ScheduleModel: недели → дни → занятия
      student_exists_model.py    # ответ /students/{zach}/exists
      student_group_model.py     # ответ /students/{zach}/group
    models/                      # ORM, файл на таблицу
      base.py                    # DeclarativeBase, общая metadata
      rating_record.py           # ведомость с контрольными точками
      grade_record.py            # ведомость без КТ, только оценка
      student_group.py           # связка «зачётка → группа»
      group_schedule.py          # расписание группы одним JSON-документом
  parser/html_parser.py          # разбор HTML ведомости в целевые JSON-форматы
  services/
    parser_service.py            # обход ASP.NET (viewstate, конкурентность, пул сессий, ретраи)
    parsing_pipeline.py          # пайплайн цикла парсинга (4 этапа) + PipelineReport
    group_extractor.py           # выбор группы студента по большинству вхождений
    rating_service.py            # чтение записей успеваемости по зачётке
    student_service.py           # проверка существования данных студента
    schedule_service.py          # чтение расписания по группе
  repository/
    rating_repository.py         # чтение снапшота
    snapshot_repository.py       # перезапись снапшота одной транзакцией
    schedule_repository.py       # чтение и полная замена расписаний
  routers/
    rating_router.py             # REST API рейтинга (/rating/...)
    students_router.py           # REST API студента (/students/...)
    schedule_router.py           # REST API расписания (/schedule/...)
  resources/rating_v2.txt        # ASCII-баннер, печатается при старте

tools/schedule_import/           # вне app: разовая загрузка расписания, бэкенд от неё не зависит
  parser.py                      # разбор выгрузок Excel в ScheduleModel по группам
  __main__.py                    # CLI: отчёт по файлам и запись в БД
  files/                         # сами выгрузки из деканатов
```

**Настройки (`config.py`)** сгруппированы по подсистемам, читающим окружение через свои префиксы: `ParsingSettings` (`PARSING_*`), `DatabaseSettings` (`DB_*`), `SchedulerSettings` (`SCHEDULER_*`), `RatingSiteSettings` (`RATING_*`), `LoggingSettings` (`LOG_*`). Чисто кодовый тюнинг, который **не выносится в `.env`**, живёт как дефолты: `ScraperSettings` (конкурентность, таймауты, ретраи), `HtmlVedSettings` (индексы колонок ведомости), `HtmlFormSettings` (имена ASP.NET-контролов).

### Пайплайн парсинга (4 этапа)
Полный цикл описан в `services/parsing_pipeline.py`. Каждый этап логирует своё начало и итог (с результатом и длительностью):

1. **checking site availability** — проверка доступности `rating.vsuet.ru`; если недоступен, цикл откладывается.
2. **collecting vedomost links** — конкурентный обход факультетов → групп, сбор ссылок на ведомости. Результат сгруппирован по названиям групп.
3. **parsing records into snapshot** — конкурентное скачивание и разбор ведомостей, запись в открытую транзакцию. Попутно из тех же данных собирается связка «зачётка → группа».
4. **committing snapshot** — COMMIT: новый снимок становится виден читателям одномоментно.

Прежде этапов было пять: у Redis нет транзакций, поэтому приходилось отдельно чистить фоновую БД перед записью и переключать указатель активной в конце. В SQLite обе задачи решает сама транзакция, и эти этапы исчезли.

По завершении планировщик пишет сводку: `parsed/empty/failed` ведомости, число записей и строк по таблицам, `students_with_group`, `loss_pct`, тайминги.

### Хранение данных
Данные — снимок сайта, целиком заменяемый каждым циклом.

* **Три таблицы** (`entities/models/`): `rating_record` — ведомости с контрольными точками (Зачёт, Экзамен); `grade_record` — оценочные ведомости; `student_group` — связка «зачётка → группа».
* **Первичный ключ** `(zach_number, ved_type, subject_name)` служит и индексом для основного запроса: `zach_number` и `ved_type` — его левый префикс, поэтому чтение идёт поиском по индексу, а не сканом.
* **`control_points` — JSON-поле**, а не отдельная таблица: контрольные точки всегда читаются целиком вместе со своей записью и по отдельности не запрашиваются. Если понадобится выборка по КТ — в SQLite есть `json_extract`, схему менять не придётся.
* **Изоляция снимков** — режим WAL: пока цикл пишет новый снимок (до нескольких минут), читатели видят прежний. Обрыв процесса посреди цикла откатывается движком, полузаписанное состояние читателям не достаётся.
* **Связка «зачётка → группа»** выводится из того же обхода, что и рейтинг: ссылки собираются по группам, а номера зачёток есть в записях ведомости. Отдельных запросов к сайту не требуется (`services/group_extractor.py`).

### Расписание занятий
Источник — выгрузки Excel из деканатов. Они лежат в репозитории
(`tools/schedule_import/files/`), потому что заново их взять негде: файлы
выдают в деканатах и меняются раз в семестр.

Загрузка — **не часть бэкенда**, а разовая ручная команда: приложение работает
и без неё, а разбор чужой разметки Excel нечего держать в рантайме API.

```bash
python -m tools.schedule_import              # вся папка files/
python -m tools.schedule_import --dry-run    # разобрать и показать отчёт
python -m tools.schedule_import путь.xlsx    # один файл или своя папка
```

Инструмент печатает отчёт по каждому файлу и **пропускает файлы чужой
разметки с указанием причины**: выгрузки обновляются в деканатах, и смена
формата должна быть видна сразу, а не через тихо пропавший факультет. Если не
разобрана ни одна группа, запись отменяется — иначе пустой результат стёр бы
всё расписание разом.

Таблица `group_schedule` заменяется целиком: выгрузки считаются единственным
источником правды, поэтому исчезнувшие из них группы уходят и из БД. Данные
рейтинга при этом не трогаются.

Разбирается недельное расписание очного отделения (файлы факультетов). Три
неочевидных места разметки: пара занимает **две строки** (верхняя — числитель,
нижняя — знаменатель); группа занимает одну колонку либо две объединённые
(тогда это подгруппы); лекция на поток лежит в ячейке, объединённой по
колонкам нескольких групп, и её значение хранится только в левой верхней.

Хранится как `ScheduleModel` (`entities/schemas/schedule.py`), сериализованный
в JSON, — документ на группу:

```json
{"numerator": {"monday": [
  {"start_time": "11:50:00", "end_time": "13:25:00",
   "name": "Иностранный язык", "lesson_type": "practice",
   "teacher_name": "Мирошниченко Е.Н.", "classroom": "21", "subgroups": [1]}
]}, "denominator": {}}
```

Занятия дня — список, отсортированный по времени начала: у подгрупп в одной
паре бывают разные занятия, и в один объект они не помещаются.
`subgroups: [1, 2]` означает «вся группа».

### Форматы записей успеваемости
* **Рейтинговый** (Зачёты/Экзамены с разбивкой по контрольным точкам): список `control_points` (КТ1–КТ4) с оценками по видам работ (лекции, практики, лаб., др.) и их весами + итоговый балл `final_rating`.
* **Оценочный** (остальные типы, а также Зачёты/Экзамены без КТ): только поле финальной оценки `grade` (приоритет отдаётся поздним пересдачам).

### Эндпоинты API Рейтинга

Все роуты принимают номер зачётной книжки в пути. `/students/...` — служебная проверка, `/rating/...` — данные успеваемости (массив записей).

| Метод | Путь | Описание |
|-------|------|----------|
| GET | `/students/{zach_number}/exists` | Есть ли какие-либо данные по зачётке (`{"zach_number": str, "exists": bool}`) |
| GET | `/students/{zach_number}/group` | Группа студента (`{"zach_number": str, "group_name": str \| null}`) |
| GET | `/schedule/groups` | Список групп, для которых загружено расписание |
| GET | `/schedule/{group_name}` | Расписание группы (`schedule: null`, если не загружено) |
| GET | `/rating/{zach_number}/zachet` | Ведомости типа «Зачёт» (рейтинговый формат) |
| GET | `/rating/{zach_number}/ekzamen` | Ведомости типа «Экзамен» (рейтинговый формат) |
| GET | `/rating/{zach_number}/vypusknaya-rabota` | Выпускные квалификационные работы |
| GET | `/rating/{zach_number}/gosekzamen` | Государственные экзамены |
| GET | `/rating/{zach_number}/kontrolnaya-rabota` | Контрольные работы |
| GET | `/rating/{zach_number}/kursovaya-rabota` | Курсовые работы |
| GET | `/rating/{zach_number}/kursovoy-proekt` | Курсовые проекты |
| GET | `/rating/{zach_number}/praktika` | Отчёты по практике |
